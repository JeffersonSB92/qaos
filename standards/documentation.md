# Documentation Standard

## Rule

Documentation must preserve useful context, decisions, and operational knowledge without unnecessarily duplicating information that already has a reliable source of truth.

## Rationale

Documentation preserves relevant knowledge, reduces loss of context, supports decisions, facilitates onboarding, and makes operation and maintenance more understandable. It helps avoid repeated rediscovery of important information. Excessive or duplicated documentation can become outdated and create conflicting guidance, so useful documentation should be deliberate and proportionate.

```text
documentation.md
= defines documentation quality rules

templates/
= provide reusable document structures

decisions/
= preserve important rationale and consequences

documentation.md
= defines how that information should remain useful and understandable

knowledge/
= research and non-normative supporting knowledge

documentation.md
= governs how useful written knowledge is structured and maintained
```

Templates support this standard; they do not replace contextual thinking.

## Requirements

**Purposeful documentation.** Every document must have a clear purpose. Documents must not be created solely because projects commonly have that kind of document.

**Source of truth awareness.** Documentation must not unnecessarily duplicate information already maintained in a reliable source of truth, such as source code, configuration, version control, project management systems, or official documentation. When duplication is necessary, its reason should be clear and the content should preferably summarize or reference the source.

**Explain why, not only what.** Documentation should preserve rationale, constraints, assumptions, decisions, and relevant context. It should avoid merely restating information that is already clear from the implementation.

**Current relevance.** Documentation used operationally must represent the current relevant understanding. Content known to be outdated must be updated, marked as outdated, superseded, archived, or removed as appropriate. This standard does not establish an archival policy.

**Decision traceability.** Material decisions should preserve enough context to understand what was decided, why, relevant consequences, and major alternatives when useful. Important decisions belong in `decisions/` when applicable.

**Audience awareness.** Documentation should use language appropriate to its intended audience. It should avoid excessive technical detail for readers who do not need it.

**Actionability.** Operational documentation should provide enough information to perform or understand the intended activity. It should avoid incomplete instructions that depend exclusively on tacit knowledge when that knowledge is relevant.

**Conciseness.** Documentation should be as detailed as necessary, but no more. It should avoid becoming a complete transcript of reasoning or irrelevant history.

**Consistent terminology.** Documentation must use terminology consistently with domain language, QAOS naming, and project vocabulary. Terms with specific meanings must be used consistently.

**Separation between reusable and client-specific knowledge.** QAOS documentation must remain generic and reusable. Client-specific documentation belongs in the client workspace. Client context must not be moved into the main QAOS merely to improve documentation.

**Sensitive information.** Documentation must not contain secrets or unnecessarily expose sensitive client information. It must remain consistent with the Client Data Handling Policy and Credentials and Secrets Policy.

**Links and references.** Documentation should prefer references and links when they reduce duplication and maintain a clear source of truth. Links should include enough surrounding context to remain understandable.

**Examples.** Examples may be used when they improve understanding, but they must avoid real client data, secrets, and proprietary code, and must remain clearly illustrative. This standard does not create a global `examples/` category.

**Version-specific information.** If documentation applies only to a specific version, environment, or period, that limitation should be explicit when materially relevant. Formal versioning is not required for every document.

**Generated documentation.** Documentation generated by agents or tools must meet the same requirements as human-authored documentation. Generated content must not be treated as automatically correct and should be reviewed for relevance, accuracy, context, and sensitive information before operational use.

The main QAOS uses Markdown as its source of truth. This repository practice must not automatically be imposed on client documentation or artifacts.

## Allowed exceptions

Exceptions may be appropriate when external compliance or contractual requirements demand duplication, a client requires a specific documentation format, legacy processes depend on existing documents, a temporary migration requires parallel sources, or operational safety requires redundant instructions.

In these cases, duplication or a special format must be intentional. A client-specific exception must not alter this global standard.

## Verification

Review adherence to this standard with questions such as:

```text
What purpose does this document serve?

Is this information already maintained elsewhere?

Does this document preserve useful rationale or context?

Could the document become misleading if the source system changes?

Is the intended audience clear?

Is the content actionable when it needs to be?

Is the document more detailed than necessary?

Are terms used consistently?

Does it contain client-specific or sensitive information that does not belong here?

Could a reference replace duplicated content?

Is generated content being reviewed rather than assumed correct?
```

These questions support review of the standard; they do not create a separate quality gate.
