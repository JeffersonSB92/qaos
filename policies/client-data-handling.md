# Client Data Handling Policy

## Purpose

This policy ensures that client information is used only for legitimate engagement objectives and remains protected during analysis, documentation, automation, and other Quality Engineering activities. Access to data does not grant unrestricted authorization to reuse it.

## Policy

Client information must be used only within the scope of the engagement for which it was provided or made accessible.

Access to client data does not make that data reusable consultancy knowledge.

Client-specific information must remain inside the corresponding client workspace or approved client systems unless an explicit delivery or authorized transfer requires otherwise.

Reusable knowledge must be extracted through abstraction, sanitization, and review rather than by copying client artifacts.

## Scope

This policy applies to information from source repositories, local files, databases, APIs, logs, screenshots, videos, test evidence, bug reports, monitoring tools, documentation, tickets, CI/CD systems, environment configuration, engagement communications, and files generated by Codex or other tools. It also applies to artifacts derived from that information.

## Data classification

### Client Confidential

Client-specific information that must not leave the workspace or authorized client systems. This includes proprietary source code, private architecture, internal business rules, private endpoints, internal documentation, logs, real customer information, production data, private tickets, and confidential reports.

### Sensitive

Information requiring additional protection, including passwords, API keys, access tokens, certificates, authentication material, personal data, private keys, and secrets. Sensitive information must receive more restrictive handling. Secrets must also follow the [[Credentials and Secrets Policy]].

### Generalized

Knowledge intentionally abstracted, sanitized, stripped of identifying client information, and reviewed for reuse. Only Generalized knowledge may become a candidate for the main QAOS. Data must not be assumed to become Generalized automatically.

## Requirements

**Need-to-use.** Access and use only the information necessary for the current task. Large volumes of data must not be copied merely for convenience.

**Local workspace.** Client-specific artifacts must remain in `project/`, `work/`, or `learnings/`, according to their nature. They must not be stored in the main QAOS.

**Source of truth.** When technical information can be verified directly in `project/`, consult that source of truth instead of permanently duplicating it in `work/`. The `work/` directory must retain useful engagement knowledge, not indiscriminate repository copies.

**Production data.** Real production data should be avoided when synthetic, anonymized, or controlled data is sufficient. When real data is necessary, use the minimum necessary, do not duplicate it unnecessarily, do not promote it to reusable knowledge, and follow client-specific restrictions.

**Screenshots and evidence.** Screenshots, recordings, and test evidence must be treated as client data when they can reveal names, emails, identifiers, business information, internal screens, environment information, customer data, tokens, or credentials. Test evidence must not be assumed safe for reuse.

**Logs.** Logs may contain sensitive data or identifiers. Before using logs in documentation or learnings, inspect them for sensitive information, remove unnecessary identifiers, and sanitize content when appropriate.

**External tools.** Client information must not be sent to external tools or services without need and authorization compatible with the engagement rules.

## Prohibited actions

- Copying client data to the main QAOS.
- Using one client's data as a dataset or example for another client.
- Storing secrets in Markdown.
- Including credentials in learnings.
- Using real data when it is not necessary.
- Copying databases or complete dumps without operational need.
- Retaining redundant copies of confidential information.
- Transforming proprietary code into a reusable example.
- Placing client screenshots in `knowledge/`.
- Using client-specific information in patterns, standards, or playbooks without abstraction and sanitization.
- Publishing or sharing internal artifacts without appropriate authorization.

## Data minimization

Collect, copy, retain, and expose only the minimum client information necessary for the current Quality Engineering objective.

This applies to analysis, debugging, documentation, automation, evidence, and reporting.

## Generated artifacts

Artifacts generated by Codex, scripts, or other tools remain client data when derived from client-specific information.

```text
project source code
      ↓
Codex analysis
      ↓
work/analysis/architecture-assessment.md
```

Generation through QAOS does not make an artifact reusable QAOS property. It remains specific to the engagement.

## Learnings and reuse

```text
client information
      ↓
project experience
      ↓
client learning
      ↓
sanitization
      ↓
generalization
      ↓
review
      ↓
QAOS learning candidate
```

Before promotion, verify that content contains no client name, internal system name, private URL, endpoint, credential, proprietary code, real data, confidential business rule, or uniquely identifying architecture detail. Promotion must be intentional and never automatic.

## Retention and cleanup

Data that is no longer necessary should be considered for removal. Temporary copies must not be retained indefinitely without reason. Engagement closure must include a review of local artifacts. Contractual or client requirements prevail when more restrictive.

## Exceptions

Exceptions must have a legitimate need, respect contractual and confidentiality obligations, use the minimum possible data, be documented when relevant, and must not permit reuse between clients.

An operational exception does not convert confidential data into reusable knowledge.
